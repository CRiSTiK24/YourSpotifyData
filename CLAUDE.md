# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Turns a Spotify GDPR data export into a personal, hostable listening-history site: a FastAPI + htmx backend that reads/writes a SQLite database, with server-rendered HTML (no template engine, no JS framework, no frontend build step).

## Commands

```bash
cd backend
uv run uvicorn src.main:app --reload   # run the app (http://localhost:8000)
uv run ruff check .                    # lint
uv run ruff format .                   # format
uv run pytest                          # run tests
```

Config lives in `backend/.env` (see README.md for the full list of vars — `DB_PATH`, `ALLOWED_EMAIL`/`RESEND_API_KEY` for login, `SPOTIFY_CLIENT_ID`/`SPOTIFY_CLIENT_SECRET` for cover art, `SPOTIFY_REDIRECT_URI` for the scrobbler). All are optional; whichever feature needs a missing var just stays unusable rather than failing startup.

Dependencies are pinned in `backend/pyproject.toml` (`uv sync` to install) — don't fall back to an ambient/shared venv, this project needs its own.

**Deployment**: this instance runs under pm2 as the `spotify` process (port 8501, not the README's default 8000). Code edits do not take effect until it's restarted:

```bash
pm2 restart spotify
pm2 logs spotify --lines 20 --nostream   # sanity-check it came back up clean
```

## Architecture

**Domain modules** (`backend/src/<domain>/` for albums, artists, auth, covers, library, playlists, scrobbler, search, theme, tracks, upload) follow a consistent split:
- `router.py` — FastAPI routes, returns `HTMLResponse` via `src/html.py` helpers (or JSON/redirects where relevant)
- `service.py` — SQLite queries (raw `sqlite3`, no ORM; `DBDep` from `src/database.py` injects a per-request connection with `row_factory = sqlite3.Row`)
- `views.py` — assembles a route's HTML out of `src/html.py` components (only present where a module has enough view logic to warrant splitting it out of `router.py`)
- `exceptions.py` — module-specific exceptions (only where needed)

**`src/html.py` is the shared component DSL** — every page is Python-generated HTML built from a small set of reusable pieces: `page()` (shell/nav/sidebar), `row()` / `card()` / `grid()` (list vs. tile layouts), `detail_layout()` (track/album/artist/playlist detail pages), `hero_image()`, `copy_list_button()`, etc. New pages should compose these rather than writing raw HTML strings, so visual/behavioral consistency (spacing, hx-boost wiring, escaping) isn't reimplemented per module.

**htmx conventions and gotchas**: the app uses `hx-boost` globally with `hx-target="#content" hx-select="#content"` set on `<body>`. Any element that issues its own `hx-get` for a fragment that doesn't contain `#content` (search dropdowns, infinite-scroll sentinels, lazy-load triggers) **must** explicitly override `hx-target`/`hx-select` on that element (`hx-target='this' hx-select='unset'` is the pattern used throughout `src/html.py`) — otherwise it inherits body's selectors, and since the fragment response has no `#content` element, that inherited select-and-swap wipes the entire page content out instead of updating just the element. Follow this same override pattern for any new fragment-loading element (see `paginated_fragment`/`infinite_scroll_trigger`/`lazy_load_trigger`/`_quick_search_widget` in `src/html.py` for the current call sites — the code itself has no comments explaining this anymore, this paragraph is the documentation).

**htmx's history-cache snapshot defaults to the entire `<body>`, not just `#content`.** `main.py`'s `#content` element carries `hx-history-elt` specifically to narrow that scope, matching how a normal boosted swap already behaves (persistent chrome — the sidebar, search box, profile switcher, the audio preview bar — is never touched). Without it, a browser-back navigation that hits htmx's local history cache (as opposed to a network refetch) silently restores *all* of that chrome to whatever it looked like at the moment you'd navigated away, independent of any state changes since — this is exactly what caused the preview player to show a stale/duplicate "now playing" track after going back (fixed, but keep the mechanism in mind for any new stateful element living outside `#content`: don't cache its DOM references at script load, `document.getElementById` fresh on every use instead, the way every `frontend/static/*.js` file now does — `preview.js` used to be the one exception). To manually check this class of bug still isn't back: play a track, navigate to a different page, play a different track there, hit back — the bar and the originally-playing button's icon should both reflect whichever track is actually still loaded in the `<audio>` element, never the one you started with.

**`htmx.min.js` is vendored locally** (`frontend/static/htmx.min.js`), not loaded from a CDN — every other script here already was, and htmx being the one exception was a real, if intermittent, failure mode (a slow/blocked CDN request silently disables `hx-boost` entirely for that pageload, degrading every link to a full navigation). To upgrade it: download the new version, verify it against the checksum published on `htmx.org`'s own release/CDN page before committing, and specifically re-check the history-restore behavior above — the local snapshot mechanism is exactly the kind of internal behavior a minor version bump could change without it showing up as an obvious breakage anywhere else.

**Code has (almost) no comments by design.** Context that would otherwise live in a docstring or inline comment belongs in a descriptive name instead wherever possible (e.g. `_is_allowed_spotify_cdn_host`, `MAX_ZIP_SIZE_COMPRESSED`, `run_periodic`'s `require_connected` param). Where a name genuinely can't carry the reasoning, the comment was stripped anyway and, if the gotcha was load-bearing, folded into this file instead — so treat CLAUDE.md, not the source, as the place to look for and add "why" context. A few gotchas worth knowing that aren't obvious from names alone:
- `src/database.py`'s `get_connection()` uses `check_same_thread=False` because the async `/upload` route resolves its `DBDep` in a different worker thread than the request handler body runs in; every other route is still one fresh connection per request, closed at the end, so there's no real concurrent-use risk.
- `src/database.py`'s `ensure_base_schema()` applies `schema.sql` unconditionally on every boot (every statement is `CREATE ... IF NOT EXISTS`, so it's a no-op against an existing DB) — this is the sole thing that makes a genuinely fresh clone (no `SpotifyData.db` yet) bootable instead of crashing on the first query against a table that was never created.
- `src/users/service.py`'s `ensure_schema()` runs `ANALYZE` after backfilling `user_id` columns/indexes: without it, SQLite's planner doesn't know the new `user_id` indexes are far less selective than the existing `(name, singer)` index on `track_history` and picks them anyway for queries filtering on both — turning an index lookup into a near-full-table scan per row (measured ~3s per playlist on 238k rows, vs ~2ms after `ANALYZE`).
- `src/scrobbler/loop.py` exists as its own module, separate from `service.py`, specifically to avoid a circular import (`service.py` needs `run_periodic`; `run_periodic` takes a `require_connected` callback rather than importing `service.get_status` directly, which would import back into `service.py`) — don't "clean this up" by merging it back into `service.py`.
- `src/scrobbler/service.py`'s `_pending_oauth_states` maps CSRF state to which user's tokens the OAuth callback should write; a plain dict+lock is sufficient since it's bounded to at most a few in-flight entries (max 5 users, one connect attempt each), same pattern as `auth/service.py`'s pending login codes.
- `src/scrobbler/service.py`'s `UNKNOWN_TRACK_NAME = "Unknown Track"` is Spotify's own placeholder for tracks it can no longer resolve metadata for (seen on removed/region-locked tracks still appearing in play history), filtered out by literal string match since the app never produces this value itself.
- `src/playlists/router.py` mounts playlist listing both under `/{username}` and at the aggregate root (pure GET), but the description-edit POST and detail GET stay `/{username}`-only, since a playlist's numeric id is only meaningful together with its owning user (`schema.sql`: `UNIQUE(user_id, name)`) — unlike albums/artists/tracks, which are keyed by name and can genuinely merge across users.
- `src/albums/service.py`'s `resolve_album_name_variants`: Spotify sometimes reports a different `album_name` string for the same release depending on the source API path (saved-albums list vs. streaming history); it resolves every name variant sharing the same `spotify_album_id` (already fetched by the cover-art job) so plays logged under any spelling are found, falling back to the literal name when no id was ever resolved. `load_album_track_history` falls back to a plain album-name match when `artist_name` is empty (a bare `/album/{name}` link with no `?artist=`), since `artist_name` is the join key into `album_images` needed to resolve variants at all.
- `src/library/router.py`'s `most_listened`: the genre carousel's own click marks its tags `hx-swap-oob` so clicking patches them in place without resetting scroll position — but *any other* request to `/most-listened` also has htmx strip that OOB element on arrival (no existing `#ml-genre-tags` to patch into yet), which would delete it before the real page swap ever inserts it. Checking the `HX-Target` header for `ml-results` is what scopes `oob=True` to just the carousel-click case.
- `src/library/views.py`'s `date_filter_html`: each field's `min`/`max` is bounded by the *other* field's currently-selected value (not just the overall data range on both), so picking a From immediately rules out a To before it — server-rendered because both fields already trigger a full reload on change, so no client-side sync is needed. The embedded `navigate()` script reads `genre` from `window.location.search` at click time rather than a value baked in at render, since a genre-tag click only swaps `#ml-results` and this script tag (in the page header, outside that swap) never re-executes when the genre changes — a closured value would silently go stale the moment a date field was touched afterward.
- `src/genres.py`'s `GENRE_ARTIST_SUBQUERY` (reused everywhere a most-listened query needs to restrict to artists tagged with a genre) is a `json_each`-based subquery, not a join, since `artist_images.genres` is a JSON array, not a normalized table; takes exactly one `?` bind param meant to sit inside an `IN (...)` clause. `load_top_genres_for_period`'s period math (`CAST(strftime('%Y%m', time) AS INTEGER)`) deliberately mirrors `track_play_counts.period` from `library/play_counts.py`'s `ensure_monthly_play_count_tables`, computed live here instead of joined from that table since it only tracks play counts, not genre.
- `home.py`'s `_load_recently_explored_albums` treats an album as "recently explored" when at least half its known tracks (`recent_tracks * 2 >= total_tracks`) got their first-ever play within the trailing window, gated by `RECENTLY_EXPLORED_ALBUMS_MIN_TRACKS` so a low-sample album (e.g. one track played twice) can't trivially qualify; it dedupes by `spotify_album_id` where known, falling back to `singer|album` — the same variant-spelling problem `albums/service.py` solves for track history.
- `src/html.py`'s `page()` includes a `<script>` reading `localStorage` theme overrides inline in `<head>`, before the stylesheet/htmx load — intentional, to avoid a flash of unstyled/default theme on load, not dead code to remove.
- `src/html.py`'s `static_url()` appends a content-hash query string to every static asset reference: `/static/*` is served with no `Cache-Control` header, so browsers fall back to heuristic caching and can keep serving stale JS/CSS indefinitely after a deploy — this was a real production bug (stale `preview.js` causing the playback-bar visual glitch to persist after the underlying fix shipped). Always reference static assets through `static_url()`, never a bare `/static/...` path.
- `src/html.py`'s `word_cloud()` assigns tag hue by alphabetical rank (not insertion/frequency order) so a given genre's color stays stable across re-renders even as play counts shift its position; its `hx-get` targets a fragment swap (`hx-target='this' hx-select='unset'`, per the htmx gotcha above) and uses `hx-swap-oob="innerHTML"` specifically to preserve `scrollLeft` on the carousel — a full-element swap would reset scroll position on every filter click. The `--wc-scale` CSS custom property it emits is read by `style.css`'s `.widget .word-cloud.carousel` rule (0.55 on narrow/carousel placement, reset to 1 at 700px) and multiplied into each tag's inline `font-size` via `calc()`, keeping relative tag-size hierarchy intact on mobile without per-tag Python recalculation per breakpoint.
- `src/html.py`'s `infinite_scroll_trigger()` fires on both an intersection observer and a manual click as a fallback — some mobile browsers don't reliably fire intersection callbacks for elements that become visible via a swap rather than a scroll.

**Color palette** is defined once in `src/palette.py` (`Palette` enum) and synced into `frontend/static/style.css`'s generated `:root` block by `sync_css_palette()` on app startup (writes between `/* palette:start */` / `/* palette:end */` markers, generated — do not hand-edit). Never hand-edit that block — change `Palette` instead.

**Responsive sizing** in `style.css` uses CSS container queries (`container-type: inline-size` on `.panel`, sizes expressed in `cqw` with `clamp()`) rather than viewport-width media queries, since layout width is driven by the panel/column an element sits in (e.g. the two-column detail-page header), not the full viewport. Follow this pattern for new size-dependent CSS rather than introducing `@media` breakpoints. `.carousel` is the deliberate exception: it uses `vw`, not `cqw`, since it never sits inside a narrower `.panel` and `cqw` requires a container-size-settling pass that's visible here as the widget growing a beat after first paint (`.widget` shrink-wraps to `.carousel`'s width); `vw` resolves in one pass with no flicker for an always-full-viewport-width element.

**`frontend/static/*.js` and `style.css` gotchas worth knowing that aren't obvious from the code alone:**
- Persistent-chrome DOM refs (the preview bar, sidebar, profile switcher) must be looked up fresh on every use (`document.getElementById` at call time), never cached at script load — the htmx history-cache-hit "back" navigation described above can replace their DOM with a stale snapshot even though it lives outside `#content`, leaving a cached reference pointing at an invisible orphaned node forever after. `preview.js` is the reference implementation (its `el(id)` helper); volume/progress-bar listeners are delegated on `document` for the same reason. All `document`-level delegation across these files exists so behavior survives `#content` being swapped by htmx with no per-page re-init needed.
- `preview.js`'s `relinkActiveBtn()` runs both immediately on `popstate` and again via `setTimeout(relinkActiveBtn, 0)`: a history-cache-hit restore can land near-instantly without going through the normal request/swap pipeline, so `htmx:afterSwap` isn't guaranteed to fire, and `popstate` itself can fire before the restore lands — losing that race left `activeBtn` wrongly `null` with nothing to correct it, since `reset(wasActive)` no-ops on `null`, leaving a stale `.playing` class stuck on the wrong button. `play()` additionally sweeps every `.playing` button (not just the tracked `activeBtn`) as a second line of defense, since a wrong `activeBtn` is exactly the case a `reset(wasActive)`-only approach can't self-correct. Restoring a saved session deliberately does not auto-play (browser autoplay-with-sound policy, plus it'd be a jarring surprise). `pageshow` re-syncs unconditionally as a bfcache-resume safety net (browsers commonly but not universally pause media and fire `pause` before freezing for bfcache). The two-`Audio`-element guard covers two causes: `window.__previewPlayerInitialized` (cheap insurance against double script execution) and, the real-world one, two browser tabs each running independent `Audio` elements — `BroadcastChannel("preview-audio")` + `postMessage("stop")` in `play()` is what actually stops cross-tab duplicate audio.
- `carousel.js`'s drag-to-scroll is mouse-only (`pointerType === "mouse"`; touch/trackpad get native scrolling free) and prevents `dragstart` on `.carousel` because images/links are natively draggable and would otherwise fight the custom drag; a capture-phase click handler checks `justDragged` before a card's link/play button fires, since a drag ending on that element would otherwise still register as a click. `style.css` reinforces this with `-webkit-user-drag: none` on `.carousel img, .carousel a` (a same-effect hint WebKit/Blink honor even earlier, no Firefox equivalent, so the JS `preventDefault()` still does the real work).
- Carousels use CSS Grid (`display:inline-grid; grid-auto-flow:column`), not flexbox, to route around a real, still-open Firefox bug (bugzilla.mozilla.org/1055887) where Firefox's flex intrinsic-sizing disagrees with Chromium when a flex container's own intrinsic width is computed from `flex-shrink:0` children — showed up as the ancestor `.widget` reserving width for cards that weren't actually rendered. Grid's intrinsic-sizing algorithm doesn't share the bug.
- Several containers (`.quick-search-results`, `.grid`, `.widget-grid`, `.ml-column`, `.heatmap-wrap`, `.heatmap-years-overview`) explicitly set `overflow-x: hidden`/`clip` alongside `overflow-y: auto` — setting only `overflow-y` auto-converts `overflow-x` from `visible` to `auto` per spec, and minor content/track rounding was enough to trigger a functionless horizontal scrollbar. An inactive `[data-tooltip]::after` bubble (up to 220px) still occupies layout space at `opacity:0` and can inflate scrollable width near an edge, so it's clipped at specific ancestors rather than globally (so `position:sticky` and upward tooltip bleed elsewhere still work). `scrollbar-gutter: stable` is used alongside these so the thumb reserves its own space instead of overlaying/shifting content. Mobile scrollbar visibility is forced persistent (`scrollbar-width`/`scrollbar-color` for Firefox, `::-webkit-scrollbar-*` for Chromium) since mobile browsers otherwise hide scrollbars at rest, making a scrollable heatmap indistinguishable from a cut-off one — iOS Safari is the one exception, it ignores `::-webkit-scrollbar` entirely for regular scroll containers (an uncircumventable OS-level restriction) and still falls back to the momentary indicator there.
- Breakpoint override rules must go at the end of `style.css`, never inline near their base (mobile-default) selector: for equal-specificity rules, the one later in source order wins regardless of which `@media` currently matches, so an override placed before its base rule gets silently clobbered the moment that base rule is next touched.
- The large-hero detail-header layout (`@media (min-width: 700px) { @container (min-width: 534px) { ... } }`) nests a container query inside a viewport query specifically to avoid a flicker right at the 700px boundary: crossing 700px independently bumps `.content`'s padding (16px→32px), which shrinks `.panel` in the same instant, and a bare container query could straddle the 534px threshold in lockstep with a mouse hovering near 700px. Nesting means the container query only evaluates after the padding jump has already happened. `.detail-header-top` uses `grid-template-rows: auto minmax(0, 1fr)` (not bare `1fr`, which still respects content's natural minimum and won't compress below it) with an explicit `height: var(--hero-size)`, otherwise the heatmap row has no definite total to size against and overflows past the image's bottom edge; the heatmap area itself uses `height:100%` of its own grid cell rather than `var(--hero-size)` directly, to avoid double-counting the title row's height. `.hero-image` and `.heatmap-years-overview` share the same `--hero-size` custom property rather than two independently-written `clamp()` expressions that could drift, and `.hm-year-row` uses `align-items: stretch` (not `center`) so that shared height reaches each row's `.hm-month-chip` via `height:100%`.
- `[hidden]` is a UA-stylesheet default (`display:none`); an author rule setting `display:flex`/`block` on the same element for its visible state silently wins over it regardless of specificity (author styles always beat UA styles) — toggling the `hidden` attribute alone doesn't work without an explicit `.foo[hidden] { display: none; }` rule placed after the base rule (see `.preview-bar[hidden]`).
- `font-display: optional` (not `swap`) is used for the Director display font: `swap` caused a visible `.widget-header` reflow when the font finished loading after first paint (not reliably fixed by preloading in Firefox). `optional` gives the font ~100ms to load before committing to the fallback for that view, trading "Director" not always appearing on a cold/slow load for zero post-paint reflow.
- `.preview-bar-progress` opts out of the page's global `border-box` reset (`box-sizing: content-box`) because its 10px padding (for a comfortable tap target around a visually 4px bar) would otherwise exceed the declared height and collapse the paintable area to nothing; it uses `--color-surface`, not `--color-bg`, for the unfilled track because `--color-bg` and `--color-nav-bg` (the bar's own background) are nearly the same near-black, making a `--color-bg` track invisible.
- `tooltips.js`'s `positionTooltip()` sets a `--tooltip-shift` (px) custom property, read by `style.css`, to nudge a `[data-tooltip]::after` bubble back into a narrow viewport/container's bounds while its `::before` arrow keeps pointing straight at the host; defaults to `0px` so it degrades gracefully with no JS.
- `--color-accent-soft`/`--color-border` (both resolve to `--light-purple`) reach only ~3.2:1 contrast against `--color-text`, below 4.5:1 AA — an accepted tradeoff on resting-state button labels and the heatmap's lightest intensity step. `--color-text` is the only color ever used for actual text; accent colors are fills/borders only.
- `hx-swap="... transition:true"` (wired globally on `<body>`) triggers the browser's native View Transition API on every boosted navigation, cross-fading `#content`; the `prefers-reduced-motion` block in `style.css` disables that animation for users who've asked for it.
- The mobile heatmap's `.hm-month-chip` header shows the month number, not an abbreviation — 1–2 letter abbreviations collide too much to stay unambiguous (Jan/Jun/Jul, Mar/May) at that width; full abbreviations return at 700px+.
- `.date-filter-field` uses `flex: 1 1 calc(50% - 6px)` with a `min-width: 140px` floor rather than sizing to each input's intrinsic width — the default wasn't wide enough on at least one mobile browser's native month-picker rendering to show a full value ("January 2026") without clipping. `input[type="date"] { color-scheme: dark; }` tells the browser this is a dark page so the native date/month picker renders with light text/controls instead of illegibly dark-on-dark.

**Cover art** goes through `/cover` (`src/covers/router.py`), a single choke point that recolors Spotify's source images into the site palette (`src/duotone.py`) and resizes server-side — restricted to Spotify's CDN hosts to avoid SSRF. `raw=true` opts an image out of recoloring (used for playlist covers).

**Background jobs**, started in `main.py`'s lifespan and run as `asyncio` tasks for the life of the process:
- scrobbler poll loop (`src/scrobbler/service.py`) — polls Spotify recently-played every `scrobbler_poll_seconds`
- library sync loop (`src/scrobbler/library_sync.py`) — syncs playlists/liked songs/liked albums/followed artists every `library_sync_poll_seconds`
- image fetch loop (`src/images/service.py`) — throttled cover-art backfill via the Spotify Web API

**Multiuser**: one **owner** account plus up to 4 **member** accounts (`src/users/`, `MAX_USERS = 5`), each with fully isolated data — every user-scoped table carries a `user_id` column (except `album_images`/`artist_images`, a deliberately shared name-keyed cover-art cache — two users' identical artist/album still share one fetch). Every content route lives under `/{username}/...`; `main.py`'s `user_router` resolves that segment via `users_service.resolve_viewed_user` (404 if unknown) and injects the target row as `ViewedUserDep`. `src/html.py`'s `u(path)` helper prepends the *current* username (a `ContextVar` set by middleware) to any in-app link/redirect — always use it instead of a bare `f"/{path}"` for anything under the user prefix.

**Auth** (`src/auth/`): login code by email via Resend, session cookie tied to a `user_id`. `require_write_access` (current user must be the owner, or exactly the `{username}` being viewed) gates Upload/Scrobbler/Profile — all unified onto one `/{username}/account` hub page (`src/account/router.py` composes each module's own content-builder function into one page; those routes' bare `GET`s now just redirect there). `require_admin` (owner, and only from their own page) additionally gates the Admin section. `can_write_var`/`is_owner_home_var` (`ContextVar`s set by the same middleware) drive sidebar visibility without threading auth state through every route.

**First run**: if no owner account exists yet, `main.py`'s middleware redirects every request to `/setup` (`src/setup/`) except `/static/*`. Completing setup requires a one-time **setup token** (Jenkins-style: generated on boot, printed to logs, persisted to `backend/.setup_token`, consumed on use) so claiming the instance needs filesystem/log access, not just being the first HTTP visitor. That page creates the owner and can set `RESEND_API_KEY`/`SPOTIFY_CLIENT_ID`/`SPOTIFY_CLIENT_SECRET`/`SPOTIFY_REDIRECT_URI`, all written via `src/app_settings.py` into a DB-backed `app_settings` table rather than `backend/.env` — `app_settings.get(con)` returns the DB value if set, else falls back to `src.config.settings`'s env-var equivalent, so existing `.env`-configured instances keep working unmigrated. Nothing here needs a restart: `create_owner` + `ensure_schema` + the settings write all run synchronously, and every consumer (auth's Resend send, the scrobbler, the image-fetch loop) re-reads `app_settings.get(con)` per use rather than caching it at startup. The owner can revisit `/setup` any time afterward to change these values (gated by `require_admin`-equivalent role check in `setup/router.py`).

**Data pipeline** (`processors/*.py`) is separate from the FastAPI app — standalone scripts that parse the raw Spotify GDPR export (`data/spotifyRaw/*.json`) into `data/spotifyProcessed/SpotifyData.db` per `data/spotifyProcessed/schema.sql`:
- `StreamingHistoryProcessor.py` — play history
- `YourLibraryProcessor.py` — liked songs/albums, followed artists
- `PlaylistProcessor.py` — playlists (safe to re-run; a playlist missing from a re-upload is deleted along with its tracks)
- `SpotifyImageFetcher.py` — the standalone/manual counterpart to the `images` background loop

`src/upload/service.py`'s web `/upload` flow deliberately only runs `StreamingHistoryProcessor.py` (`UPLOAD_PROCESSOR_SCRIPTS`) — liked songs/albums/followed artists and playlists come from the scrobbler's live library sync (`src/scrobbler/library_sync.py`) instead, not from re-uploading the export.

Search (`src/search/`) uses a SQLite FTS5 virtual table (`track_history_fts`) kept in sync with `track_history` via triggers defined in `schema.sql`, rather than `LIKE '%word%'` scans — the table has 200k+ rows.

**Testing** (`backend/tests/`, run via `uv run pytest`) follows a strict gate before any test gets written, adapted from PostHog's own internal testing philosophy: before writing a test, name the specific regression it would catch — a concrete bug, code path, and input that would break. If you can't name it, don't write the test; coverage-chasing and change-detector tests (asserting internal call order/private-method mocking) are explicitly not wanted here. Cheapest-first: prefer a pure-function unit test (no DB/network) over a DB-backed test over a full endpoint test — extract logic into a pure function first if that's what it takes to test it cheaply. When a test does need I/O, mock only true external boundaries (network calls, the Spotify/Resend APIs) — never internal helpers or private methods. `tests/conftest.py`'s `db` fixture gives a fresh in-memory SQLite DB built from the real `data/spotifyProcessed/schema.sql` per test, so DB-backed tests (e.g. `test_play_counts.py`, which exercises the `track_play_counts`/`album_play_counts`/`artist_play_counts` trigger-maintained bookkeeping — the most correctness-critical logic in the app) run against real schema and triggers, not a mock.
